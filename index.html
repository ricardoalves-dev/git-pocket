Configuração
Configure identidade, editor, aliases e preferências globais do Git
5
git config
Define configurações do Git (nome, e-mail, editor, etc.)
Use ao configurar um ambiente pela primeira vez ou ao ajustar preferências. O flag --global aplica para todos os repositórios do usuário; sem ele, aplica apenas ao repositório atual.
# Definir nome e e-mail globalmente
git config --global user.name "Seu Nome"
git config --global user.email "seu@email.com"

# Definir editor padrão
git config --global core.editor "code --wait"

# Listar todas as configurações
git config --list
git config alias
Cria atalhos (aliases) para comandos longos
Ideal para economizar tempo com comandos frequentes. Chame o alias com git <alias>.
# Criar alias "st" para "status"
git config --global alias.st status

# Alias para log formatado
git config --global alias.lg "log --oneline --graph --decorate --all"

# Usar o alias
git lg
git config credential.helper
Configura o armazenamento de credenciais
Use para não precisar digitar usuário/senha (ou token) a cada push/pull em repositórios HTTPS.
# Armazenar em memória por 1 hora
git config --global credential.helper "cache --timeout=3600"

# Armazenar permanentemente no disco
git config --global credential.helper store
⚠️
Atenção
O modo store salva as credenciais em texto puro no disco (~/.git-credentials). Prefira usar SSH ou um gerenciador de credenciais do sistema operacional.
git config pull.rebase
Define a estratégia padrão do git pull (merge ou rebase)
Configure uma vez para evitar o aviso que o Git exibe ao rodar git pull sem definição explícita.
# Usar rebase ao invés de merge no pull
git config --global pull.rebase true

# Usar merge (padrão tradicional)
git config --global pull.rebase false
.gitignore
Lista de padrões de arquivos/pastas que o Git deve ignorar
Crie na raiz do projeto para excluir artefatos de build, variáveis de ambiente, dependências e arquivos pessoais do versionamento.
# Criar ou editar .gitignore
echo "node_modules/" >> .gitignore
echo ".env" >> .gitignore
echo "dist/" >> .gitignore

# Verificar quais arquivos o Git está rastreando
git ls-files
Use gitignore.io para gerar templates prontos para sua stack.

Inicialização e Clonagem
Crie um novo repositório do zero ou obtenha uma cópia de um existente
3
git init
Inicializa um repositório Git em um diretório
Use ao começar um projeto do zero, antes de fazer o primeiro commit. Cria a pasta oculta .git/ com toda a estrutura interna.
# Inicializar no diretório atual
git init

# Inicializar em uma nova pasta
git init meu-projeto
git clone
Clona um repositório remoto para a máquina local
Use para obter uma cópia completa (histórico incluso) de um repositório existente. Aceita URLs HTTPS ou SSH.
# Clonar via HTTPS
git clone https://github.com/usuario/repo.git

# Clonar via SSH (recomendado)
git clone git@github.com:usuario/repo.git

# Clonar em uma pasta com nome diferente
git clone git@github.com:usuario/repo.git minha-pasta

# Clonar apenas a branch principal (mais rápido)
git clone --depth=1 git@github.com:usuario/repo.git
git remote
Gerencia conexões com repositórios remotos
Use após git init para vincular o repositório local a um remoto, ou para gerenciar múltiplos remotos (ex: origin e upstream).
# Adicionar um remoto
git remote add origin git@github.com:usuario/repo.git

# Listar remotos e suas URLs
git remote -v

# Alterar a URL de um remoto
git remote set-url origin git@github.com:usuario/novo-repo.git

# Remover um remoto
git remote remove origin

Inspeção e Status
Visualize o estado atual, diferenças e o histórico do repositório
6
git status
Exibe o estado atual da árvore de trabalho
Use com frequência para saber quais arquivos foram modificados, quais estão na área de staging e quais são novos (untracked). É o comando mais consultado do dia a dia.
# Status detalhado
git status

# Formato curto/resumido
git status -s
git diff
Mostra as diferenças entre versões de arquivos
Use para revisar exatamente o que mudou antes de fazer um commit, ou para comparar branches.
# Diff de arquivos não staged
git diff

# Diff de arquivos já adicionados ao staging
git diff --staged

# Comparar duas branches
git diff main..feature/minha-feature

# Diff de um arquivo específico
git diff src/arquivo.ts
git log
Exibe o histórico de commits
Use para navegar no histórico, entender o que foi alterado e por quem. Altamente configurável com flags de formatação.
# Log padrão
git log

# Log resumido (uma linha por commit)
git log --oneline

# Log com grafo de branches
git log --oneline --graph --decorate --all

# Log dos últimos 5 commits
git log -5

# Log de um arquivo específico
git log --follow src/arquivo.ts

# Buscar por mensagem de commit
git log --grep="fix:"
git show
Exibe detalhes de um commit específico
Use para inspecionar exatamente o que um commit alterou, incluindo o diff completo das mudanças.
# Detalhes do último commit
git show

# Detalhes de um commit pelo hash
git show a1b2c3d

# Mostrar apenas os arquivos alterados
git show --stat a1b2c3d

# Exibir conteúdo de um arquivo em um commit
git show a1b2c3d:src/arquivo.ts
git blame
Mostra quem alterou cada linha de um arquivo e em qual commit
Use para investigar a origem de um trecho de código, entender o contexto de uma mudança ou rastrear um bug.
# Blame de um arquivo
git blame src/arquivo.ts

# Blame com hash curto
git blame -s src/arquivo.ts

# Blame de linhas específicas (10 a 25)
git blame -L 10,25 src/arquivo.ts
git ls-files
Lista todos os arquivos que o Git está rastreando
Útil para verificar se um arquivo está sendo ignorado, se foi adicionado corretamente ao repositório ou para auditar o conteúdo.
# Listar arquivos rastreados
git ls-files

# Listar arquivos ignorados
git ls-files --others --ignored --exclude-standard

Staging e Commits
Prepare alterações e registre snapshots do projeto no histórico
5
git add
Adiciona arquivos à área de staging (index)
Use para selecionar quais mudanças farão parte do próximo commit. Prefira adicionar arquivos específicos a usar git add . indiscriminadamente.
# Adicionar um arquivo específico
git add src/arquivo.ts

# Adicionar todos os arquivos alterados
git add .

# Adicionar interativamente (escolhe hunks)
git add -p

# Adicionar todos os .ts do diretório
git add src/*.ts
Use git add -p para revisar cada bloco de mudança antes de adicionar — excelente para criar commits atômicos e bem focados.
git commit
Registra as mudanças do staging no histórico do repositório
Use após preparar o staging com git add. Escreva mensagens claras e objetivas — prefira o padrão Conventional Commits.
# Commit com mensagem inline
git commit -m "feat: adiciona tela de login"

# Adicionar e commitar arquivos já rastreados
git commit -am "fix: corrige validação do formulário"

# Abrir editor para mensagem detalhada
git commit

# Commit vazio (útil para disparar CI)
git commit --allow-empty -m "ci: trigger pipeline"
git commit --amend
Modifica o último commit (mensagem e/ou conteúdo)
Use logo após um commit para corrigir a mensagem ou incluir um arquivo esquecido, antes de fazer push.
# Corrigir apenas a mensagem do último commit
git commit --amend -m "feat: mensagem corrigida"

# Incluir arquivo esquecido sem mudar a mensagem
git add arquivo-esquecido.ts
git commit --amend --no-edit
🚨
Perigo — Reescreve histórico
--amend substitui o commit por um novo (hash diferente). Nunca use em commits que já foram enviados para um branch compartilhado — isso causará conflito de histórico para toda a equipe que fez pull.
git restore
Descarta mudanças em arquivos ou remove do staging
Use para reverter um arquivo ao seu estado no último commit (working tree) ou para removê-lo do staging sem perder as alterações locais.
# Descartar mudanças no working tree
git restore src/arquivo.ts

# Remover arquivo do staging (mantém as mudanças)
git restore --staged src/arquivo.ts

# Restaurar como estava em um commit específico
git restore --source=a1b2c3d src/arquivo.ts
🚨
Perigo — Perda de dados
git restore sem --staged descarta as mudanças do working tree permanentemente. Não há como desfazer com git reflog se as mudanças ainda não foram commitadas.
git rm
Remove arquivos do rastreamento do Git (e opcionalmente do disco)
Use quando quiser parar de versionar um arquivo. Com --cached, remove apenas do Git mas mantém o arquivo no disco.
# Remover do Git e do disco
git rm arquivo.txt

# Parar de rastrear sem deletar (comum para .env)
git rm --cached .env

# Remover pasta inteira do rastreamento
git rm -r --cached dist/
🌿
Branches
Crie, navegue, renomeie e exclua branches de trabalho
5
git branch
Lista, cria, renomeia e deleta branches
Use para gerenciar o ciclo de vida das branches. Para criar e já mudar para ela, prefira git switch -c.
# Listar branches locais
git branch

# Listar branches remotas e locais
git branch -a

# Criar nova branch
git branch feature/login

# Renomear a branch atual
git branch -m novo-nome

# Deletar branch local (apenas se merged)
git branch -d feature/login

# Forçar exclusão da branch local
git branch -D feature/login
⚠️
Atenção
A flag -D deleta a branch mesmo que ela não tenha sido integrada (merged). Use com cautela para não perder commits.
git switch
Muda para outra branch (substituto moderno do git checkout para branches)
Prefira git switch ao git checkout quando o objetivo for apenas trocar de branch — a semântica é mais clara.
# Mudar para branch existente
git switch main

# Criar e mudar para nova branch
git switch -c feature/minha-feature

# Voltar para a branch anterior
git switch -

# Criar branch a partir de um commit
git switch -c hotfix/bug a1b2c3d
git checkout
Muda de branch ou restaura arquivos (comando clássico, mais abrangente)
Ainda amplamente usado. Para trocar de branch prefira git switch; para restaurar arquivos, prefira git restore. Mas é importante conhecer pois aparece muito em docs e tutoriais.
# Mudar de branch
git checkout main

# Criar e mudar para nova branch
git checkout -b feature/nova

# Restaurar arquivo de um commit anterior
git checkout a1b2c3d -- src/arquivo.ts

# "Detached HEAD": ir para um commit específico
git checkout a1b2c3d
⚠️
Detached HEAD
Ao fazer checkout de um hash diretamente, você entra no modo detached HEAD. Qualquer commit feito aqui ficará sem referência. Crie uma branch com git switch -c nome-branch antes de commitar.
git merge
Integra o histórico de uma branch na branch atual
Use para incorporar mudanças de uma feature branch na branch principal. Gera um merge commit (preserva o histórico de ambas as branches).
# Merge de feature na branch atual
git merge feature/login

# Fast-forward apenas (sem merge commit)
git merge --ff-only feature/login

# Sempre criar merge commit (sem fast-forward)
git merge --no-ff feature/login

# Abortar um merge em conflito
git merge --abort
git rebase
Reaplica commits de uma branch sobre outra, criando um histórico linear
Use para manter a branch atualizada com a main sem criar merge commits, ou para reorganizar commits antes de abrir um PR.
# Rebasear feature na main atualizada
git switch feature/login
git rebase main

# Rebase interativo (reorganizar/editar últimos 3 commits)
git rebase -i HEAD~3

# Continuar após resolver conflito
git rebase --continue

# Abortar o rebase
git rebase --abort
🚨
Perigo — Reescreve histórico
Rebase reescreve os hashes dos commits. Nunca faça rebase de branches que outros membros da equipe já fizeram pull — isso causará divergência de histórico e conflitos difíceis de resolver. Use apenas em branches pessoais/locais não compartilhadas.
🌐
Sincronização com Remoto
Envie, receba e sincronize commits com repositórios remotos
4
git fetch
Baixa atualizações do remoto sem integrar ao working tree
Use para obter o estado atual do remoto sem mexer nos seus arquivos. Depois você decide se faz merge ou rebase. É mais seguro que git pull.
# Buscar todos os remotos
git fetch

# Buscar um remoto específico
git fetch origin

# Buscar e remover branches deletadas no remoto
git fetch --prune

# Após fetch, ver o que mudou
git log HEAD..origin/main --oneline
git pull
Busca atualizações do remoto e integra na branch atual (fetch + merge/rebase)
Use para atualizar sua branch local com as mudanças do remoto. Prefira usar com --rebase para manter histórico linear.
# Pull padrão (fetch + merge)
git pull

# Pull com rebase (histórico mais limpo)
git pull --rebase

# Pull de uma branch específica
git pull origin main

# Pull e remover branches deletadas no remoto
git pull --prune
git push
Envia commits locais para o repositório remoto
Use após commitar localmente para publicar suas mudanças. Na primeira vez em uma nova branch, use -u para definir o upstream.
# Push da branch atual
git push

# Primeiro push de uma nova branch
git push -u origin feature/login

# Push de uma tag específica
git push origin v1.0.0

# Push de todas as tags
git push --tags

# Deletar branch remota
git push origin --delete feature/login
🚨
Perigo — Force Push
Nunca use git push --force em branches compartilhadas (main, develop). Isso sobrescreve o histórico remoto e pode apagar commits de colegas. Se precisar usar, prefira git push --force-with-lease, que aborta caso o remoto tenha novos commits que você não tem localmente.
git push --force-with-lease
Versão segura do force push — aborta se o remoto tiver commits desconhecidos
Use após um rebase ou amend em uma branch pessoal para atualizar o remoto. Mais seguro que --force.
# Force push seguro
git push --force-with-lease

# Com remote e branch explícitos
git push --force-with-lease origin feature/minha-branch
Mesmo com --force-with-lease, evite force push em branches compartilhadas. Reserve para branches pessoais de PR.
↩️
Desfazendo Alterações
Reverta arquivos, commits e estados do repositório com segurança
3
git revert
Cria um novo commit que desfaz as mudanças de um commit anterior
É a forma segura de desfazer commits já publicados (pushed). Não reescreve histórico — adiciona um commit de reversão. Use sempre que precisar desfazer algo em branches compartilhadas.
# Reverter o último commit
git revert HEAD

# Reverter sem abrir editor de mensagem
git revert HEAD --no-edit

# Reverter um commit específico
git revert a1b2c3d

# Reverter múltiplos commits (do mais recente ao mais antigo)
git revert HEAD~3..HEAD
Use git revert em branches públicas/compartilhadas. Prefira git reset apenas em commits locais ainda não publicados.
git clean
Remove arquivos não rastreados do diretório de trabalho
Use para limpar arquivos gerados (builds, artefatos) que não estão no .gitignore ou para ter um working tree completamente limpo.
# Simular o que seria removido (dry-run)
git clean -n

# Remover arquivos não rastreados
git clean -f

# Remover arquivos e diretórios não rastreados
git clean -fd

# Remover também arquivos ignorados (.gitignore)
git clean -fdx
🚨
Perigo — Perda Permanente
git clean -f deleta arquivos do disco sem possibilidade de recuperação via Git. Sempre execute git clean -n primeiro para ver o que será removido antes de confirmar.
git reflog
Exibe o histórico de todas as referências (HEAD, branches), incluindo commits "perdidos"
Use para recuperar commits após um reset --hard ou branch deletada acidentalmente. O reflog é a sua rede de segurança.
# Ver histórico do HEAD
git reflog

# Recuperar após reset --hard acidental
git reflog
# Identificar o hash do commit perdido, então:
git reset --hard a1b2c3d

# Recriar branch a partir de commit perdido
git switch -c recuperado a1b2c3d
O reflog expira por padrão em 90 dias. É sua maior ferramenta de recuperação em situações de emergência.

Remoção e Reescrita de Commits
Mova, remova ou reorganize commits — operações que reescrevem o histórico
4
git reset — modos de operação
git reset --soft
Move o HEAD para um commit anterior, mantendo todas as mudanças no staging
Use para "descommitar" mantendo os arquivos prontos para um novo commit. Ideal para juntar vários commits em um só antes do push.
# Desfazer o último commit (mantém no staging)
git reset --soft HEAD~1

# Desfazer os últimos 3 commits
git reset --soft HEAD~3

# Os arquivos continuam staged — agora commit de novo
git commit -m "feat: commit unificado"
git reset --mixed
Move o HEAD e limpa o staging, mas mantém as mudanças no working tree (modo padrão)
Use para desfazer um commit e o git add, mantendo os arquivos modificados no disco. Permite reorganizar o que vai para o próximo commit.
# Desfazer último commit e unstage (padrão)
git reset HEAD~1

# Equivalente explícito
git reset --mixed HEAD~1

# Unstage de um arquivo específico sem mover HEAD
git reset HEAD src/arquivo.ts
git reset --hard
Move o HEAD e descarta todas as mudanças (staging + working tree)
Use para descartar completamente commits locais e voltar a um estado anterior. Use apenas em commits não publicados.
# Descartar o último commit completamente
git reset --hard HEAD~1

# Voltar ao estado do remoto (descartar commits locais)
git reset --hard origin/main

# Voltar para um commit específico
git reset --hard a1b2c3d
🚨
Perigo — Dados Perdidos Permanentemente
git reset --hard apaga commits e mudanças sem recuperação fácil. Mudanças não commitadas são irrecuperáveis. Commits podem ser recuperados via git reflog por até 90 dias. Nunca use em branches compartilhadas após o push — force push seria necessário e causaria danos à equipe.
git rebase -i — reorganização interativa
git rebase -i
Rebase interativo: edite, junte, reordene ou remova commits
Use antes de abrir um PR para limpar o histórico: juntar commits de WIP, corrigir mensagens, remover commits de debug, reordenar logicamente.
# Editar os últimos 4 commits
git rebase -i HEAD~4

# No editor que abre, comandos disponíveis:
# pick   — mantém o commit
# reword — mantém mas edita a mensagem
# edit   — pausa para amend
# squash — une ao commit anterior (mantém msg)
# fixup  — une ao commit anterior (descarta msg)
# drop   — remove o commit completamente
🚨
Perigo — Reescreve histórico
O rebase interativo reescreve todos os hashes a partir do ponto selecionado. Use apenas em branches locais não compartilhadas. Após o rebase, será necessário git push --force-with-lease.
🗂️
Stash — Trabalho Temporário
Salve e restaure mudanças em progresso sem precisar commitá-las
5
git stash
Guarda temporariamente mudanças não commitadas em uma pilha
Use quando precisar mudar de branch urgentemente sem querer commitar um trabalho incompleto. O stash limpa o working tree para um estado limpo.
# Guardar mudanças com mensagem descritiva
git stash push -m "wip: implementando tela de perfil"

# Forma curta (sem mensagem)
git stash

# Incluir arquivos novos (untracked)
git stash -u

# Guardar apenas arquivos específicos
git stash push -m "wip" src/componente.ts
git stash list
Lista todas as entradas na pilha de stash
Use para ver o que está guardado antes de restaurar. Cada entrada é identificada por stash@{n}.
# Listar stashes
git stash list

# Ver o diff de um stash específico
git stash show -p stash@{0}
git stash pop
Restaura o stash mais recente e o remove da pilha
Use para retomar um trabalho guardado. Se houver conflitos, resolva-os manualmente — o stash não é removido automaticamente em caso de conflito.
# Restaurar o stash mais recente
git stash pop

# Restaurar um stash específico pelo índice
git stash pop stash@{2}
git stash apply
Aplica o stash sem removê-lo da pilha
Use quando quiser aplicar o mesmo stash em múltiplas branches, ou quando não tiver certeza se vai querer o stash disponível depois.
# Aplicar sem remover da pilha
git stash apply stash@{0}
git stash drop / clear
Remove uma entrada ou limpa toda a pilha de stash
Use para limpar stashes antigos que não são mais necessários.
# Remover um stash específico
git stash drop stash@{1}

# Remover todos os stashes
git stash clear
⚠️
Atenção
git stash clear remove todos os stashes permanentemente. Verifique com git stash list antes de executar.
🏷️
Tags e Releases
Marque pontos específicos do histórico para versões e releases
4
git tag
Cria uma referência permanente (tag) para um commit
Use para marcar versões de release (v1.0.0, v2.3.1). Tags anotadas (-a) são preferíveis pois armazenam metadados do autor e data.
# Listar todas as tags
git tag

# Tag simples (lightweight)
git tag v1.0.0

# Tag anotada (recomendada para releases)
git tag -a v1.0.0 -m "Release versão 1.0.0"

# Tag em um commit específico
git tag -a v0.9.0 a1b2c3d -m "Beta release"
git push --tags
Envia tags para o repositório remoto
Tags não são enviadas automaticamente com git push. Envie explicitamente após criar.
# Enviar uma tag específica
git push origin v1.0.0

# Enviar todas as tags locais
git push --tags

# Deletar uma tag no remoto
git push origin --delete v1.0.0-beta
git tag -d
Remove uma tag local
Use para corrigir uma tag criada no commit errado ou com nome incorreto.
# Deletar tag local
git tag -d v1.0.0-errada

# Depois deletar do remoto também
git push origin --delete v1.0.0-errada
git describe
Descreve o commit atual em relação à tag mais próxima
Útil em scripts de build para gerar versões dinâmicas baseadas nas tags do repositório.
# Descrever o commit atual
git describe --tags
# Saída exemplo: v1.2.0-5-ga1b2c3d
# (tag + nº de commits desde a tag + hash)

Ferramentas Avançadas
Cherry-pick, bisect, worktree e outros comandos para situações específicas
5
git cherry-pick
Aplica as mudanças de um commit específico na branch atual
Use para trazer um fix pontual de outra branch sem fazer merge completo. Muito útil em hotfixes que precisam ser aplicados na produção.
# Aplicar um commit específico
git cherry-pick a1b2c3d

# Cherry-pick sem criar commit (fica no staging)
git cherry-pick -n a1b2c3d

# Cherry-pick de um range de commits
git cherry-pick a1b2c3d..f4e5d6c

# Continuar após resolver conflito
git cherry-pick --continue

# Abortar
git cherry-pick --abort
git bisect
Busca binária no histórico para encontrar qual commit introduziu um bug
Use quando souber que um bug existia em um commit antigo mas não no atual (ou vice-versa). O Git faz uma busca binária testando commits automaticamente.
# Iniciar bisect
git bisect start

# Marcar commit atual como ruim (tem o bug)
git bisect bad

# Marcar commit antigo como bom (sem o bug)
git bisect good v1.0.0

# Git faz checkout de commits intermediários
# Você testa e marca: good ou bad
git bisect good
git bisect bad

# Git identifica o commit culpado

# Finalizar e voltar ao HEAD
git bisect reset
git worktree
Cria múltiplas árvores de trabalho a partir do mesmo repositório
Use quando precisar trabalhar em duas branches simultaneamente sem fazer stash ou alternar entre elas — útil para revisar um PR enquanto desenvolve outra feature.
# Criar novo worktree para uma branch
git worktree add ../projeto-hotfix hotfix/bug-critico

# Criar worktree com nova branch
git worktree add -b review/pr-123 ../pr-review origin/pr-123

# Listar worktrees
git worktree list

# Remover worktree
git worktree remove ../projeto-hotfix
git grep
Pesquisa padrões de texto nos arquivos rastreados pelo repositório
Use para encontrar ocorrências de uma string ou regex no código. Mais rápido que o grep do sistema em repositórios grandes pois usa o índice do Git.
# Buscar uma string no código
git grep "useState"

# Buscar com número da linha
git grep -n "TODO"

# Buscar em um commit específico
git grep "função" HEAD~5

# Buscar apenas em arquivos .ts
git grep "interface" -- "*.ts"
git shortlog
Exibe resumo do número de commits por autor
Use para ter uma visão rápida das contribuições de cada membro da equipe no repositório.
# Resumo por autor
git shortlog -sn

# Resumo do último mês
git shortlog -sn --since="1 month ago"

Submódulos
Gerencie repositórios Git aninhados dentro de outro repositório
4
git submodule add
Adiciona um repositório externo como submódulo do projeto atual
Use quando precisar incluir uma dependência como código-fonte versionado junto ao projeto, com controle de versão independente.
# Adicionar submódulo
git submodule add git@github.com:org/lib.git libs/minha-lib

# Clonar repositório que contém submódulos
git clone --recurse-submodules git@github.com:org/repo.git
⚠️
Complexidade extra
Submódulos adicionam complexidade ao fluxo de trabalho. Considere alternativas como gerenciadores de pacotes (npm, Maven) antes de optar por submódulos.
git submodule update
Inicializa e atualiza os submódulos para os commits registrados no repositório pai
Use após clonar um repositório com submódulos, ou após um pull que atualizou as referências dos submódulos.
# Inicializar e atualizar todos os submódulos
git submodule update --init --recursive

# Atualizar para o HEAD do remoto
git submodule update --remote
git submodule foreach
Executa um comando em cada submódulo
Use para rodar operações em lote em todos os submódulos, como pull, status ou build.
# Fazer pull em todos os submódulos
git submodule foreach 'git pull origin main'

# Ver status de cada submódulo
git submodule foreach git status
git submodule deinit
Remove a configuração local de um submódulo sem deletá-lo do histórico
Use para desativar um submódulo localmente ou antes de removê-lo completamente do projeto.
# Desativar um submódulo
git submodule deinit libs/minha-lib

# Remover completamente (deinit + rm + git rm)
git submodule deinit libs/minha-lib
git rm libs/minha-lib
rm -rf .git/modules/libs/minha-lib

GitFlow
Modelo de ramificação estruturado para projetos com ciclos de release bem definidos
6
O que é GitFlow
GitFlow é um modelo de ramificação (branching model) criado por Vincent Driessen que define um conjunto de regras sobre como criar, nomear e mesclar branches durante o ciclo de vida de um projeto
Use GitFlow quando seu projeto tem:
  • Ciclos de release planejados (versões v1.0, v1.1, v2.0…)
  • Múltiplos desenvolvedores trabalhando em paralelo
  • Necessidade de manter uma versão estável em produção enquanto o desenvolvimento continua
  • Processo formal de QA/homologação antes de cada release

Evite GitFlow quando:
  • O projeto usa entrega contínua (CI/CD com deploy a cada commit)
  • A equipe é pequena e o ritmo de entrega é alto — o overhead de branches pode ser desnecessário

O modelo define 5 tipos de branches com papéis específicos:

Branch Papel Duração
main Código de produção — apenas versões estáveis Permanente
develop Integração contínua — onde features se encontram Permanente
feature/* Desenvolvimento de novas funcionalidades Temporária
release/* Preparação e ajustes finais de uma versão Temporária
hotfix/* Correções urgentes direto em produção Temporária 
# Diagrama simplificado do GitFlow:
#
#  main     ──●────────────────────────●──────────●──
#              \                       /↑          /↑
#  develop   ───●──●──●──●──────●──●──  \    ●───   \
#                   \     \    /    \    \  / \      \
#  feature        ───●──●──  ───●     release  hotfix
Setup inicial do GitFlow
Prepara o repositório com a estrutura de branches do GitFlow — pode ser feito com a extensão git-flow ou manualmente
Faça o setup uma única vez no início do projeto, ou ao adotar GitFlow em um repositório existente. A extensão git-flow automatiza os merges e a criação de branches; sem ela, você executa os mesmos passos manualmente.
── Com a extensão git-flow (recomendado) ────────────
# Instalar (macOS)
brew install git-flow-avh

# Instalar (Linux)
apt-get install git-flow

# Inicializar no repositório (aceite os nomes padrão)
git flow init
# → pergunta os nomes das branches; pressione Enter para aceitar os padrões

── Manualmente (sem a extensão) ─────────────────────
git switch -c develop
git push origin develop
# (main já existe; basta criar develop a partir dela)
GitFlow — Fluxo de Feature
Como criar, desenvolver e integrar uma nova funcionalidade seguindo o GitFlow
Toda nova funcionalidade parte de develop e retorna para develop ao final. Nunca mergeia direto em main. A feature só vai para produção quando uma release for aberta.
── Com a extensão git-flow ───────────────────────────
# Iniciar feature (cria branch feature/pagamento-pix a partir de develop)
git flow feature start pagamento-pix

# Desenvolva normalmente com commits
git add .
git commit -m "feat: implementa integração com API do Pix"

# Finalizar (merge em develop + deleta a branch)
git flow feature finish pagamento-pix

── Manualmente ──────────────────────────────────────
git switch develop && git pull origin develop
git switch -c feature/pagamento-pix

# ... commits ...

git switch develop
git merge --no-ff feature/pagamento-pix
git branch -d feature/pagamento-pix
git push origin develop
💡
Por que --no-ff?
O flag --no-ff (no fast-forward) força a criação de um commit de merge, preservando no histórico a informação de que aquele grupo de commits pertencia a uma feature. Sem ele, o histórico fica linear e perde esse contexto.
GitFlow — Fluxo de Release
Abre uma janela de estabilização antes de lançar a versão: apenas bugfixes, bump de versão e ajustes de documentação são permitidos
Abra uma release quando develop já contém todas as features da próxima versão e está pronto para QA. Nenhuma feature nova entra na release — apenas correções de bugs encontrados nessa fase. Ao finalizar, a release vai para main (com tag) e também de volta para develop.
── Com a extensão git-flow ───────────────────────────
# Abrir release (parte de develop)
git flow release start 1.2.0

# Faça apenas bugfixes e bump de versão
git commit -m "chore: bump version to 1.2.0"

# Finalizar: merge em main + tag + merge em develop + deleta branch
git flow release finish 1.2.0
git push origin main develop --tags

── Manualmente ──────────────────────────────────────
git switch develop && git pull origin develop
git switch -c release/1.2.0

# ... ajustes finais ...

# Merge em main com tag
git switch main
git merge --no-ff release/1.2.0
git tag -a v1.2.0 -m "Release 1.2.0"

# Merge de volta em develop (para incluir os bugfixes da release)
git switch develop
git merge --no-ff release/1.2.0

git branch -d release/1.2.0
git push origin main develop --tags
GitFlow — Fluxo de Hotfix
Correção emergencial que parte diretamente de main, sem passar por develop, garantindo que código em desenvolvimento não contamine a correção
Use quando há um bug crítico em produção e develop já possui commits que não estão prontos para ir a produção. O hotfix é a única branch temporária que parte de main. Ao finalizar, vai para main (com tag) e para develop.
── Com a extensão git-flow ───────────────────────────
# Abrir hotfix (parte de main)
git flow hotfix start 1.2.1

# Faça a correção
git commit -m "fix: corrige crash ao expirar sessão"

# Finalizar: merge em main + tag + merge em develop
git flow hotfix finish 1.2.1
git push origin main develop --tags

── Manualmente ──────────────────────────────────────
git switch main && git pull origin main
git switch -c hotfix/1.2.1

# ... correção ...

git switch main
git merge --no-ff hotfix/1.2.1
git tag -a v1.2.1 -m "Hotfix: crash na sessão"

git switch develop
git merge --no-ff hotfix/1.2.1

git branch -d hotfix/1.2.1
git push origin main develop --tags
Alternativas ao GitFlow
GitFlow não é bala de prata — conheça as alternativas para escolher o modelo certo para cada contexto
O GitFlow brilha em projetos com releases versionadas e múltiplos ambientes. Para outros contextos, modelos mais simples entregam o mesmo controle com menos overhead.
── GitHub Flow (para CI/CD e deploy contínuo) ────────
# Apenas duas regras:
# 1. main é sempre deployável
# 2. Qualquer trabalho novo parte de main via feature branch
git switch -c feat/minha-feature
# → abre PR → revisão → merge em main → deploy automático

── Trunk-Based Development (para times avançados) ───
# Todos commitam direto em main (ou em branches de vida curtíssima)
# Requer feature flags para esconder funcionalidades incompletas
# Menor overhead, maior disciplina

── Resumo rápido ─────────────────────────────────────
# GitFlow      → releases versionadas, múltiplos ambientes
# GitHub Flow  → SaaS, deploy contínuo, times ágeis
# Trunk-Based  → times maduros com boa cobertura de testes

Fluxos e Solução de Problemas
Cenários completos do dia a dia: conflitos, commits errados, branch errada e recuperação de histórico
7
Feature Branch Workflow
Fluxo completo para desenvolver uma nova funcionalidade sem impactar a branch principal
Adote este fluxo sempre que for iniciar qualquer tarefa nova — seja uma feature, bugfix ou melhoria. Ele isola seu trabalho, facilita revisão de código e evita quebrar a branch principal.
# 1. Garanta que seu ponto de partida está atualizado
git switch main
git pull origin main

# 2. Crie uma branch descritiva para a tarefa
git switch -c feat/login-com-google

# 3. Desenvolva normalmente, fazendo commits atômicos
git add .
git commit -m "feat: adiciona botão de login com Google"

# 4. Mantenha sua branch atualizada com main durante o desenvolvimento
git fetch origin
git rebase origin/main

# 5. Publique e abra o Pull Request
git push origin feat/login-com-google

# 6. Após aprovação e merge, limpe localmente
git switch main
git pull origin main
git branch -d feat/login-com-google
Resolver conflito de merge
Passo a passo para resolver conflitos que surgem ao mesclar duas branches com alterações no mesmo trecho de código
Conflitos acontecem quando dois commits modificam as mesmas linhas de um arquivo. O Git não sabe qual versão prevalece — cabe a você decidir. O processo é sempre o mesmo: identificar → editar → marcar resolvido → continuar.
# Ao rodar merge e haver conflito, o Git avisa:
# CONFLICT (content): Merge conflict in src/auth.ts
# Automatic merge failed; fix conflicts and then commit.

# 1. Veja quais arquivos estão em conflito
git status
# → both modified: src/auth.ts

# 2. Abra o arquivo — o Git marca as divergências assim:
# <<<<<<< HEAD          ← sua versão atual
# const url = '/login';
# =======                ← separador
# const url = '/auth';   ← versão que vem do merge
# >>>>>>> feat/nova-rota

# 3. Edite o arquivo: remova os marcadores e deixe o código correto

# 4. Marque o conflito como resolvido
git add src/auth.ts

# 5. Finalize o merge
git commit
# (o Git sugere uma mensagem de merge — pode aceitar ou personalizar)
💡
Dica
Use git merge --abort para cancelar todo o merge e voltar ao estado anterior, caso prefira recomeçar.
Resolver conflito de rebase
Como lidar com conflitos durante um git rebase, que aplica commits um a um
No rebase, se houver conflito, o processo para no commit problemático para você resolver antes de continuar. Diferente do merge (um único conflito), no rebase você pode ter que resolver conflitos em vários commits sequencialmente.
# Rebase parou com conflito — resolva o arquivo normalmente
# (edite, remova os marcadores <<<, ===, >>>)

# Marque como resolvido
git add src/auth.ts

# Continue o rebase (NÃO use git commit aqui!)
git rebase --continue

# Se o próximo commit também tiver conflito, repita o processo

# Para abortar e voltar ao estado original
git rebase --abort

# Para pular o commit conflitante (use com cuidado)
git rebase --skip
Corrigir ou desfazer o último commit
Três formas de consertar o commit mais recente antes de publicá-lo no remoto
Use enquanto o commit ainda não foi enviado com push. Depois do push, reescrever o histórico causa problemas para quem já baixou.
── Opção A: corrigir apenas a mensagem ──────────────
git commit --amend -m "fix: mensagem corrigida"

── Opção B: incluir mais arquivos no commit ─────────
git add arquivo-esquecido.ts
git commit --amend --no-edit
# (mantém a mesma mensagem)

── Opção C: desfazer o commit, mantendo as alterações
git reset HEAD~1
# → arquivos voltam para unstaged; você edita e refaz o commit

── Opção D: descartar o commit E as alterações ──────
git reset --hard HEAD~1
⚠️
Atenção
--hard descarta as alterações permanentemente. Use apenas se tiver certeza de que não precisa do código.
Commit feito na branch errada
Como mover um ou mais commits para a branch correta quando você commitou no lugar errado
Acontece quando você esquece de criar/trocar de branch antes de começar a trabalhar. O cherry-pick copia os commits para o destino certo; depois você os remove da branch de origem.
# Cenário: você fez commits em 'main' que deveriam estar em 'feat/minha-feature'

# 1. Anote o hash dos commits que serão movidos
git log --oneline -5
# ex: a1b2c3d feat: novo componente de tabela

# 2. Vá para a branch de destino e aplique o commit
git switch feat/minha-feature
git cherry-pick a1b2c3d

# 3. Volte para a branch de origem e remova o commit de lá
git switch main
git reset --hard HEAD~1
# (ajuste o número se forem mais de 1 commit)
💡
Se o commit já foi publicado em main
Não use reset --hard em histórico público. Prefira git revert <hash> para criar um commit que desfaz o efeito, sem reescrever o histórico.
Recuperar commits perdidos com reflog
O reflog é o "histórico dos históricos" — registra para onde HEAD apontou, permitindo recuperar commits após um reset --hard ou exclusão acidental de branch
Use sempre que achar que perdeu trabalho por um reset, rebase mal feito ou branch deletada. O reflog guarda os ponteiros por 90 dias por padrão.
# 1. Veja o histórico de movimentos do HEAD
git reflog
# Saída exemplo:
# a1b2c3d HEAD@{0}: reset: moving to HEAD~2
# f4e5d6c HEAD@{1}: commit: feat: formulário de contato   ← commit perdido!
# 9g8h7i6 HEAD@{2}: commit: fix: validação de e-mail

# 2. Restaure o estado que você quer
git reset --hard HEAD@{1}
# ou crie uma nova branch a partir do ponto perdido
git switch -c recuperado HEAD@{1}
Hotfix em produção
Fluxo para corrigir um bug crítico diretamente em produção sem incluir código incompleto que está em desenvolvimento
Use quando há um bug urgente em produção e a branch main/master já possui commits novos que não podem ir para produção ainda. O hotfix parte diretamente da tag ou branch de release estável.
# 1. Parta da branch/tag estável de produção
git switch main
git pull origin main
git switch -c hotfix/corrige-crash-login

# 2. Faça a correção e commite
git add .
git commit -m "fix: corrige crash no login com sessão expirada"

# 3. Merge de volta para main E para a branch de desenvolvimento
git switch main
git merge --no-ff hotfix/corrige-crash-login
git tag -a v1.2.1 -m "Hotfix: crash no login"
git push origin main --tags

# 4. Leve a correção também para a branch de desenvolvimento
git switch develop
git merge --no-ff hotfix/corrige-crash-login
git push origin develop

# 5. Limpe a branch de hotfix
git branch -d hotfix/corrige-crash-login
